你有没有这样的体验？

每天打开 GitHub Trending，看到几十个新项目冒出来，心里想着「这个不错，star 一下」。打开 Hacker News，首页又是十几个 AI 相关的帖子，标题都很诱人。

然后呢？

收藏了一堆链接，存了一堆书签，加了一堆 Read It Later。一周后回头看——一个都没读过。

这不是你一个人的问题。在 AI 领域，每天产生的技术内容呈指数级增长。GitHub 上每天都有上百个新仓库获得 50+ stars，Hacker News 每天有几百条 AI 相关讨论。靠人力去筛选、阅读、整理，根本不现实。

那如果——让 AI 来做这件事呢？

不是那种「帮我总结一下这个网页」的简单指令。而是一个完整的自动化系统：每天自动采集、逐条深度分析、打分排序、结构化存储。你每天只需要花 5 分钟看结果。

这就是我今天要分享的：一个用 Claude Code 搭建的 AI 知识库系统。不需要写复杂的代码，核心全靠自然语言描述。

整个过程全自动。你唯一需要做的是：每天花几分钟看结果。

系统架构：四层设计

这个系统的核心设计思想是分层。一共四层，每层各司其职：

第一层：CLAUDE.md — 全局宪法

这是整个项目的「最高法律」。它定义了技术栈、编码规范、项目结构、JSON Schema，以及红线——那些绝对不能做的事。Claude Code 每次对话都会自动加载这个文件，确保所有行为都遵守规则。

第二层：Agents — 角色定义

三个 Agent，各管一段工序。Collector（采集）负责「找得全、抓得准」，Analyzer（分析）负责「读得深、评得准」，Organizer（整理）负责「去重校验入库」。每个 Agent 只定义「做什么」和「输出什么」，不关心具体怎么做。

第三层：Skills — 执行手册

Agent 的「手脚」。比如 github-trending 这个 Skill，详细规定了从搜索 API、过滤关键词、去重、写摘要到输出 JSON 的每一步 SOP。Agent 只需要调用这个 Skill，按步骤执行即可。

第四层：Knowledge — 数据产物

最终的数据存储。raw/ 保存采集原始数据（供审计和重跑），articles/ 保存经分析、去重、校验后的结构化知识条目。所有数据都是 JSON 文件，文件名包含日期和来源。

打个比方：如果你开一家公司，CLAUDE.md 是公司章程，Agents 是各部门的职责说明书，Skills 是每个岗位的 SOP 操作手册，Knowledge 是最终的产品仓库。

这个设计的好处是：每一层都可以独立演进。想增加一个新的采集源？加一个 Skill 文件就行，Agent 和 CLAUDE.md 都不需要改。想调整评分标准？只改 Analyzer 的定义，不影响采集流程。

几个关键的设计决策

在搭建过程中，有几个设计决策值得单独聊聊。这些不是技术细节，而是思维方式。

1. 为什么采集和分析要拆成两个 Skill？

直觉上，采集完直接分析，一步到位不就行了吗？

但仔细想想：它们的执行时机和频率不同。采集可以一天跑多次——上午抓一波 GitHub，下午补一波 HN。但分析只需要在当天最后一次采集后跑一次，消费所有原始数据。如果合成一个 Skill，每次采集都强制跑分析，既浪费算力，又可能产生重复的分析结果。

更重要的原因是可复用性。将来如果加了 Hacker News 的采集 Skill，tech-summary 这个分析 Skill 照样能消费它的输出，一行代码都不用改。

2. 为什么 collector 和 analyzer 不能写文件？

这是系统的第一条红线：禁止直接写入生产知识库。

为什么要这么严格？因为如果每个 Agent 都能自由写文件，你很快就会得到一个混乱的数据仓库——格式不一致、重复数据满天飞、错误的摘要混入其中。

所以我把权限做了硬隔离：只有 Organizer（整理 Agent）有写入权限。Collector 和 Analyzer 只能通过返回 JSON 来传递数据。Organizer 在写入之前，会做去重检查、Schema 校验，确保每一条入库的数据都是合格的。

这就像工厂的流水线：采集车间和生产车间只负责加工，最终质检和入库由专门的质检部门把关。

3. 为什么用 CLAUDE.md 而不是配置文件？

CLAUDE.md 是 Claude Code 的项目级配置文件，每次对话自动加载。用它的好处是自然语言即配置。

传统方式下，你需要写 YAML、JSON、TOML 来定义规则。但自然语言的表达力远超任何配置格式。比如「禁止裸 print()——统一使用 logging 模块」，用代码写要好几行，用自然语言一句话就说清楚了。

更重要的是，AI 能理解意图。配置文件只能机械执行，但 CLAUDE.md 里的规则，AI 会在具体场景中灵活应用。比如红线里写着「禁止跳过 JSON Schema 校验」，AI 在写入数据前会自动做校验，而不需要你写具体的校验代码。

4. 评分体系：为什么 9-10 分不超过 2 个？

如果让 AI 自由评分，它很容易陷入「老好人模式」——大部分项目都给 7-8 分，评分失去区分度。

所以我设计了一个硬约束：每批 15 个项目中，9-10 分（改变格局级）不超过 2 个。这倒逼 AI 严格按标准打分，大部分项目会落在 5-8 分区间。

评分标准：

9-10 改变格局 — 开创性技术或范式转移
7-8 直接有帮助 — 可直接用于生产的高质量工具
5-6 值得了解 — 有一定创新性，特定场景有用
1-4 可略过 — 同质化、营销为主、无实质贡献

搭建过程

好消息是：这个系统的核心逻辑不需要写代码。全部用自然语言描述，Claude Code 负责执行。

第一步：写 CLAUDE.md

这是整个项目的起点。你只需要告诉 AI：这个项目是什么、用什么技术栈、有哪些规范、哪些事绝对不能做。

比如我的 CLAUDE.md 里写了：

## 红线（绝对禁止）

1. 禁止直接写入生产知识库
2. 禁止硬编码 API Key / Token
3. 禁止在采集循环中使用同步阻塞 I/O
4. 禁止跳过 JSON Schema 校验
5. 禁止裸 print() 调试输出
6. 禁止覆盖已有知识条目
7. 禁止在 Agent 间传递未序列化的对象

七条红线，清清楚楚。AI 看了就知道什么能做、什么不能做。

第二步：定义 Agent 角色

创建三个 Agent 文件，每个文件用 Markdown 描述这个角色的职责和输出格式。

比如 Collector Agent 的定义：

采集 Agent — collector

流水线第一道工序。
只负责「找得全、抓得准」，不写入任何文件。

## 输出契约

返回给下游的统一 JSON 数组，两个源合并后 ≥ 15 条：
{
  "title": "文章/项目标题",
  "url": "完整 HTTPS 链接",
  "source": "github_trending | hacker_news",
  "popularity": { "stars": "int", "score": "int" },
  "summary": "简要描述（50 字以内）"
}

注意关键设计：输出契约。它明确规定了 Collector 必须返回什么格式的数据，以及最低数量要求（≥ 15 条）。这保证了下游 Analyzer 拿到的数据是可预期的。

第三步：写 Skill SOP

Skill 是最细粒度的执行手册。比如 GitHub Trending 的采集 Skill，详细规定了 7 个步骤：

1 搜索热门仓库（GitHub Search API，多时间窗口并行）
2 提取关键信息（仓库名、URL、Stars、语言、Topics）
3 双向过滤（AI 关键词纳入 + awesome-list 排除）
4 去重（与近 7 天历史文件比对 URL）
5 阅读 README，撰写中文摘要
6 按 Stars 降序取 Top 15
7 输出结构化 JSON 文件

有了这个 SOP，不管是谁（或者哪个 AI 模型）来执行，都能得到一致的结果。这就是流程标准化的价值。

第四步：跑起来

配置文件写好后，只需要对 Claude Code 说一句：

/github-trending

Claude Code 就会按照 Skill 定义的 SOP，自动搜索 API、过滤、去重、读 README、写摘要、输出 JSON。整个过程大概 2-3 分钟。

写在最后

这个系统的核心价值不在于技术本身，而在于一种新的知识管理思路：

不是你去找知识，
而是让知识主动来找你。

传统方式是「我主动搜索 → 筛选 → 阅读 → 整理」，每一步都需要消耗你的注意力和时间。新方式是「AI 帮你做完所有事，你只需要看结果」。

而且这个思路不局限于 AI 领域。你可以用同样的架构来追踪：

任何你感兴趣的技术领域（Web3、Security、DevOps…）

行业动态（竞品监控、政策变化、市场趋势）

学术前沿（论文追踪、实验室动态）

只需要换一套关键词和采集源，整个系统就能迁移过去。
